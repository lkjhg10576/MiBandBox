## 〇、换源：包名 + 签名证书（本版主线）

分发平台把上一版打回，理由两条：**「用了 AIoT 的 debug 证书签名，不是 release 包」**与**「包名不符合反向域名（Java 包命名）规范」**。本版一并处理：

- **包名**：`com.miband.bandbox` → **`com.lkjhg.bandbox`**。旧名反写域名是 `bandbox.miband.com`，`miband` 是小米自家品牌域名，三方应用占用该命名空间会被判包名不正确。新名符合反向域名规范（小写、点分段、每段字母开头、≥3 段）。
- **证书**：改用**自签发行证书**，CN = 包名（`CN=com.lkjhg.bandbox`）。此前用的是工具链自带的默认证书 `CN=localhost` —— 那就是 debug 证书，平台一眼就能认出。历史包用的那张证书已退役，不再参与签名。证书 subject 按官网「生成证书」要求带齐 7 项（国家名称 `C`、省份 `ST`、城市 `L`、组织名称 `O`、组织单位名称 `OU`、名称与姓氏 `CN`、邮箱地址 `emailAddress`）—— 缺一项就不构成合格的签名文件。
- **对老用户的影响**：**包名变了 = 另一个应用**。手环上新旧包可共存、互不覆盖；想换成新包要先按名卸载旧包（`adb shell pm uninstall com.miband.bandbox`），旧包里的本地数据不会自动迁移。平台侧的 `0.1.0`（旧包名）已下架，新包需要在控制台按新包名重新创建应用条目（控制台包名不可更改）。
- **手机插件要重装**：插件按包名寻址手环应用，目标包名变了。手机端还装着旧 abp 的话，**先卸载再装本目录里的 `BandBox辅助.abp`**，否则歌词 / 动态口令链路直接不通（诊断卡的「插件：」行会显示旧目标包名）。

## 一、打包方式与版本策略（本版确立，后续沿用）

- **发行版通道走 production 模式**（`aiot release`）：JS 压缩混淆、剔除 `.map`、用发行证书签名；Beta 通道仍是 development 模式（`aiot build`，不压缩不混淆）。
- **rpk 文件名里的 `.debug.` / `.release.` 段只表示打包模式，不是包名**。包名始终是 `com.lkjhg.bandbox`，`manifest.json` 的 `config.debug` 为 `false`。
- **发行证书必须自签、CN 等于包名、subject 7 项齐全**：缺证书、用成工具链自带的 `CN=localhost` debug 证书、CN 与包名对不上、或 subject 少了省份/城市/组织单位/邮箱，打包脚本与门禁 R12 都会直接拦下（不再兜底复制默认证书）。生成：`bash tools/gen-release-cert.sh`；只想改 subject 字段（不动私钥、不改签名身份、老用户可覆盖升级）用 `bash tools/gen-release-cert.sh --force`。
- **双端版本号对齐**：手环端快应用 `com.lkjhg.bandbox` 与手机插件 `BandBox辅助` 从本版开始共用同一个版本号（`0.1.1`）。装完应用就装同号插件，不再需要对照两套版本号。
- **`versionCode` 为 `256`**：换源后平台上是新应用，旧包的号（`0.1.0 / 221`）已随下架作废，`256` 也从未成功上架过，沿用它不与任何在架版本撞号。**从 `0.1.2` 起恢复「最大号 + 1」的严格递增取号**（`--code <n>` 可显式指定）。
- **上架分发平台**：平台只认包内 `manifest.json` 的 `versionName`/`versionCode`，控制台不会改已签名包的版本（改任一字节都会让手环验签失败、装不上）。上传前用 `node tools/verify-rpk.mjs <rpk>` 核对包内版本、包名、证书 CN 与验签结果，打包脚本出包后也会自动逐个校验。
- **双包体发行**：与手环机型一一对应，同包名 `com.lkjhg.bandbox`，按 rpk 文件名区分：

  | rpk | 适用机型 | 屏幕 |
  |---|---|---|
  | `com.lkjhg.bandbox.release.0.1.1.rpk` | 小米手环 10 / 10 NFC（212×520 跑道屏） | 212 × 520 |
  | `com.lkjhg.bandbox.pro.release.0.1.1.rpk` | 小米手环 9 Pro / 10 Pro | 336 × 480 |

  手机插件 `BandBox辅助.abp` 两端通用。

## 四、门禁与校验

静态门禁 `node tools/release-gate.mjs` 十四项全过：

- R2 / R3 埋点开关：`perf.js` 的 `ENABLED` 为 `false`，启动路径零打点；
- R4 Vela 约束：全包 `.ux` 无 `data` 与 `private` 共存；
- R5 路由对齐：路由与页面文件一一对齐；
- R6 版本一致：`manifest.json`、`package.json`、关于页、设置页、`README.md` 一致；
- R7 模板事件处理器不得撞 Node 全局标识符（否则点击静默失效）；

- R9 资源尺寸匹配 profile（`shadow.png` 等）；
- R10 计算器几何常量与 CSS 自洽；
- R11 包名规范：包名符合反向域名（Java 包命名）规范；
- R12 发行证书：证书存在、CN 不是 `localhost`、CN 与包名一致、subject 7 项齐全；
- R13 AstroBox 资源清单引用完整性（`manifest_v2.json` 里的资源引用必须在仓库里真实存在）；
- R14 发行产物完整性：`release/`、`beta/` 下每个 rpk 必须带签名块、包内不混装别的包、`SHA256SUMS.txt` 与磁盘文件对得上。

## 六、标准版包（band10）修复记录（2026-11-17）

首发时 `com.lkjhg.bandbox.release.0.1.1.rpk`（小米手环 10 / 10 NFC）在**签名之后**被二次改写，导致包内签名块丢失 → **手环拒绝安装、渠道也判「不是 release 包」**。现已还原为首发原包。

- **根因**：该文件在 2026-11-15 23:37 由工具链正常构建并签名（`META-INF/CERT` + rpk 签名块齐全），但 2026-11-16 23:24 又被改写：包根目录被塞进 `BandBox辅助.abp` 与 Pro 版 rpk 两个多余文件，rpk 签名块（`RPK Sig Block 42`）被破坏 —— `node tools/verify-rpk.mjs` 报「包内没有签名块：这是未签名的包」。`SHA256SUMS.txt` 记录的原始摘要 `26a144cb…` 与改写后的 `9d6bb47f…` 对不上，佐证改写发生在校验和生成之后。
- **不是 jsc 的问题**：两个包都是 jsc 字节码版（`app.jsc` 与 `pages/*/*.jsc` 均为真字节码，magic `01` + 模块名表），内容与原构建一致。装不上是因为**签名没了**，不是没走 jsc。
- **波及范围**：只污染了 `release/BandBox-0.1.1/` 里的这一份副本。`downloads/`（分发平台下载入口 `xmb10` / `xmb10nfc` 指向的文件）与 Pro 版包、`.abp` 自始至终未被改写，摘要与首发一致。
- **修复方式**：用 `downloads/` 里那份未被改写的原包（`26a144cb…`）**还原** `release/BandBox-0.1.1/` 里的标准版包 —— 发行目录与平台下载入口现在是同一份字节，摘要回到首发值 `26a144cb…`。
- **另外验证过**：用 0.1.1 对应的源码状态（提交 `404fba8`）在仓库原始路径下走 production 通道（`aiot release --enable-jsc` + 自签发行证书）重新构建了一份，逐文件比对与原包 **75 个 `.jsc` 与全部资源文件字节完全一致**，仅 `META-INF/CERT`、`META-INF/build.txt`、`manifest.json` 因构建时间戳与签名而不同 —— 既证明流水线能原样复现这个产物，也证明原包本身没有内容问题。
- **防复发**：`tools/verify-rpk.mjs` 新增「包内多余文件」检查（包根出现 `.rpk` / `.abp` 等非快应用资源直接判失败），打包脚本出包时与**产物落盘后**各校验一次；`tools/release-gate.mjs` 新增 **R14** 规则 —— 每次构建前扫描 `release/`、`beta/` 下所有产物，签名块缺失 / 包内混装 / 校验和与磁盘对不上，一律拦下构建。
