> **本版定位**：`0.1.2` 线的第四个 Beta。主线是**小米手环 11 支持**（212×520 跑道屏，Vela 5，与手环 10 同几何、沿用同一标准包）。本版只有一处实质改动：**修复内置输入法在手环 11 真机上不弹出的问题**；band10 / pro336 / band9 三档机型布局**零改动**（修复前后键盘态截图逐像素一致，见「三、验证」）。

## 〇、现象与真机证据

手环 11 真机装标准包（`com.lkjhg.bandbox`）后，除键盘外一切正常，唯独**点任何输入框都弹不出内置输入法**；同系统（Vela 5）的 SDK 模拟器上不复现。

真机逐层观察（本次修复的定案依据）：

1. 点输入框后，**输入卡正常进入键盘态**（卡片变矮、底部「完成」按钮消失）→ 点击命中判定、页面 `kbShow` 数据流、组件 `hide` prop 传播**全部正常**。
2. 键盘区**「完成」栏正常显示**，但**按键区一片空白**。

即：组件子树已创建、根容器定位与高度测量正常，**只有绝对定位的那部分子树没被布局**。

## 一、根因：Band 11 固件严格执行「if-div 必须有 CSS 规则」

`docs/emulator-fix.md` 记着一条 Vela 渲染规则：

> 带 `if` 的 div 必须有 CSS 规则（position + left/top + width/height），否则里面的绝对定位子元素不会被布局。

`src/components/InputMethod/InputMethod.ux` 恰好有两处违规：

- L6 懒建包装 `<div if="{{!hide || keyboardCreated}}">` —— **无任何 class/style**；
- L21 键盘主体 `<div if="{{screentype==='pill-shaped'}}" style="width:100%;height:305px">` —— **只有内联样式、无 class、无 position**。

而键盘内容几乎全是绝对定位：按键区 L22（`position:absolute`）、控制栏 L80、下展候选面板 L101。band10 / Pro / band9 的引擎与 SDK 模拟器对这条规则**宽容**，故不复现；**手环 11 固件严格执行** → 这三块整棵不布局，只剩流内的「完成」栏 —— 与真机现象逐条吻合。

## 二、修复：给每个 if/show 包装层补完整几何类（保持布局原点不变）

`src/components/InputMethod/InputMethod.ux`：

- 新增四个类，每个带 position + left/top + width/height：
  - `kbOuter`（L6 外层 if）：`absolute; left:0; top:0; 100% × 365px`
  - `kbInner`（L7 show 层）：`absolute; left:0; top:0; 100% × 365px`，原内联黑底/列向移入类
  - `kbBody`（L21 键盘体）：**`absolute; left:0; top:60px; 100% × 305px`**
  - `kbDown`（L101 下展面板）：`absolute; left:0; top:47px; 100% × 263px`
- 根容器高度由 `{{hide ? '0px' : 'auto'}}` 改为 `{{hide ? '0px' : '365px'}}`（365 = 完成栏 32 + 拼音行 28 + 键盘体 305，三机型不变量），`overflow` 恒 `hidden`。

**`kbBody` 的 `top:60px` 是本次修复的关键**。Vela 的绝对定位子节点挂在**直接父节点的布局原点**上，而不是根容器 —— 这是用 band9 终验截图 `.zcode/shots/band9-v4/ret/r01-nb-kb.png` 逐行量出来的：完成栏 y101..132、控制栏白字 y167..196、search 灰条 y211..264、按键 y280..442，全部吻合「键盘体流内原点 161 = 根顶 101 + 32 + 28」，而不吻合「以根 101 为基准」（那会让控制栏压住完成栏）。

所以 `kbBody` 必须定位在根原点下方 60px（= 32 完成栏 + 28 拼音行），把键盘体原点钉在 161，与改造前完全一致；其三个绝对定位子节点（按键区 top34 → y195、控制栏 top0 → y161、下展面板 top47 → y208）坐标逐一不变。**若误写 `top:0`，整棵按键子树上移 60px，控制栏盖住完成栏，所有机型回归。**

顺带加固（同文件）：`screenWidth` 原先靠 `device.getInfo` 异步赋值（data 默认 336、无 fail 回调、偏移又绑定在 `static` 节点上），改为直接取构建期常量 `SCREEN.w`（`src/common/layout.js`，按 profile 生成：band10=212 / band9=192 / pro336=336），首帧即正确，也不再依赖运行时 API。**模板里的 `{{(screenWidth - 192)/2}}` 等表达式字面量一字未动** —— `profiles/pro336.json` 对该文件有 14 条替换对精确命中这些子串。

## 四、附带修复：`apply-profile.mjs` 的基线备份污染

物化一个非基线 profile 时，`backup()` 只检查**目标 profile 自己的**替换串。在 pro 物化态直接切另一个非基线 profile 时，它认不出「这是 pro 态」，会把 pro 内容拍成基线备份（基线就此被污染），随后替换对又因找不到基线串而中止，源码树停在混合态（本次实测踩到，已用 `git checkout -- src/` + 重建备份目录恢复）。

修法：`backup()` 改用「任一非基线 profile 的替换串」判据（与 `refreshBackups()` 一致），并在 `materialize()` 前置检查 —— 树若停在别的非基线 profile 物化态，直接报错并提示先还原基线，不再带着污染风险往下走。**切 profile 前先还原基线**这条规矩也写进了构建脚本的用法注释。
